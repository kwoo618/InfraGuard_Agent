# 03. 모니터링 대시보드 명세

## 목표

스케일링 전/후 트래픽 결과를 **실측값으로** 보여주고, 그 결과를 발표 증빙으로 남긴다.

두 개의 화면을 역할별로 나눈다.
- **Grafana**: 부하 테스트 중 실시간 인프라 상태 (TPS, P95, 에러율, replica 수)
- **InfraGuard UI 결과 패널**: 라운드별 측정 결과 비교 (진단 → 스케일링 → 재측정)

## 금지 사항

- 목업/샘플/랜덤 데이터로 차트를 채우지 않는다. 데이터가 없으면 "측정값 없음"을 표시한다.
- 외부 CDN을 쓰지 않는다 (시연장 네트워크 리스크). 차트 라이브러리가 필요하면 `backend/app/static/vendor/`에 파일로 포함하거나, 의존성 없는 SVG로 구현한다.
- `schemas.py`, `state.py`의 기존 필드와 `/report`의 기존 응답 필드는 변경·삭제하지 않는다.
- 가드레일 값(01_개발계획.md)을 바꾸지 않는다.

## 우선순위

13:00 마감 기준 **Phase 1~4 필수**, Phase 5는 시간이 남으면 진행한다.
Phase마다 완료 기준을 직접 확인하고 커밋한 뒤 다음 Phase로 넘어간다.

## Phase 2. 로드밸런서 추가 (ISSUE-1)

**선행 확인:** Phase 1 완료 후 replica 3개 상태에서 기존 방식대로 부하를 주고
`sum by (instance) (rate(http_requests_total[1m]))`로 분산 여부를 먼저 기록한다 (02_알려진이슈.md ISSUE-1).

**작업**
- `docker-compose.yml`에 nginx 서비스 추가. target-server replica들로 요청을 분산한다.
- 스케일 후 새 replica가 nginx에 반영되는 방식을 정하고, 그 근거를 PR 설명에 적는다.
  (예: Docker DNS resolver `127.0.0.11` + 변수 proxy_pass 방식, 또는 스케일 후 nginx reload)
- 포트 (구현 기준으로 정정): target-server의 호스트 포트 매핑(`8080-8089`)을 없애고 nginx가 호스트 8080을 고정으로 받는다.
  범위 매핑이 사라지므로 포트 겹침(Locust 웹 UI 8089 포함)이 없어지고, 재생성 후 8080이 비는 문제(ISSUE-9)도 함께 해결된다.
- 부하 대상 주소 (구현 기준으로 정정): nginx가 8080을 받으므로 `.env.example`의 `TARGET_SERVER_URL`,
  `infra/locust/locust.conf`의 `host`, `run_load_test.py` 기본값(`http://localhost:8080`)은 바꾸지 않는다.
  `docker-compose.yml` backend 환경변수만 `http://nginx:8080`으로 바꾼다.
  **주의: locust.conf는 ASCII만 허용** (한글 주석 넣으면 Windows에서 크래시 — 파일 내 NOTE 참고).
- 새 replica 반영 (구현): nginx upstream `server target-server:8080 resolve` (오픈소스 1.27.3+, `nginx:1.28-alpine`),
  `resolver 127.0.0.11 valid=2s`. 근거는 `infra/nginx/nginx.conf` 주석.
- 스케일 직후 재측정에 기동 중 replica가 섞이지 않도록 `scale_service`가 `docker compose up --wait`로 healthy까지 기다린다.
- Prometheus는 nginx가 아니라 replica를 직접 수집한다 (Phase 1 설정 유지).
- README의 포트/실행 안내 갱신.

**완료 기준**
- [x] replica 3개에서 부하 테스트 시 `sum by (instance)(rate(http_requests_total[1m]))`로 3개 replica 모두 요청 수신 확인
  (2026-09-11: 32.48 / 32.07 / 32.31 req/s, 02_알려진이슈.md ISSUE-1)
- [x] replica 1 → 3 스케일 직후에도 새 replica로 요청이 들어감 (scale_service 반환 후 10~15초에 수신 관측, ISSUE-1)
- [x] UI에서 진단 시작 → 승인 → 스케일링 → 재측정 전체 흐름 정상 동작
  (진단은 일반 흐름으로 확인. 승인 → 스케일링 → 재측정은 `force_scaling`으로 확인했다.
  일반 흐름에서 LLM이 스케일 불필요로 판단한 원인은 ISSUE-3, 후속 이슈에서 처리)
- [x] `pytest tests/` 통과 (97 passed, e2e는 비스케일 경로)

## Phase 3. 라운드별 측정 이력 + 결과 파일 저장 (ISSUE-5)

**작업**
- `backend/app/api/v1/agent.py`에 task별 측정 이력 저장소 추가 (기존 `before_measurements` 패턴과 동일하게,
  state.py는 수정하지 않음).
- 부하 테스트 결과가 나올 때마다(최초 진단, 스케일링 후 재측정) 한 건씩 누적한다. 레코드 필드:
  `round`, `phase`("initial" | "after_scaling"), `replicas`, `tps`, `latency_p95`, `latency_avg`,
  `error_rate`, `total_requests`, `duration`, `target_tps`, `timestamp`
  - `replicas`는 `scale_service.get_current_replicas()` 또는 `scaling_result.after_replicas`의 **실제 값**을 쓴다.
- `/report` 응답에 `measurement_history` 필드를 **추가**한다 (기존 필드 유지).
- task 종료 시 `results/{YYYYMMDD_HHMMSS}_{task_id}.json`에 저장: 측정 이력 + 진단 결과 + 스케일링 결과 + 측정 조건
  (target_tps, duration, locustfile 엔드포인트 가중치).
- 테스트 추가: 이력 누적, `/report` 신규 필드, 파일 저장 (기존 테스트 규칙: `tmp_path` 사용, 실제 Locust/Docker 실행 X).

**완료 기준**
- [ ] 스케일링 1회 흐름 실행 후 `/report`의 `measurement_history`에 2건 (initial, after_scaling)
- [ ] `results/`에 JSON 파일 생성, 값이 UI 로그의 측정값과 일치
- [ ] 기존 `/report` 필드 그대로 존재
- [ ] `pytest tests/` 통과

## Phase 4. UI 결과 비교 패널

**작업** (`backend/app/static/`)
- 리포트 단계에서 결과 패널 표시:
  - 비교 카드: 스케일링 전/후 TPS, P95, 에러율, replica 수와 변화량 (값이 나빠졌으면 나빠진 대로 표시)
  - 라운드별 차트: x축 round, TPS와 P95 추이, replica 수 표기
  - 측정 조건 표시: target_tps, duration, replica 수
- 데이터 출처는 `/report`의 `measurement_history`만 사용한다.
- Grafana 대시보드로 가는 링크 버튼 (http://localhost:3000).
- 기존 로그 출력과 진행 단계 표시는 유지한다.

**완료 기준**
- [ ] 실제 흐름 1회 실행 후 패널 수치 = `results/` JSON 수치
- [ ] 측정 이력이 없을 때 빈 차트가 아니라 "측정값 없음" 표시
- [ ] 네트워크를 끈 상태에서도 차트 렌더링 (CDN 미사용 확인)

## 발표용 측정 절차 (Phase 4 완료 후)

1. 측정 조건 고정: PC 사양 기록, target_tps / duration 고정, 시작 replica 1
2. 같은 조건으로 **3회 이상** 반복 실행 → `results/` 파일 전부 보관
3. 발표에는 반복 결과의 범위 또는 중앙값을 쓰고, 측정 조건을 슬라이드에 함께 적는다
4. 개선이 작거나 없으면 그대로 보고하고 원인을 분석한다. 수치를 조정하지 않는다.
