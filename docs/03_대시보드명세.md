# 03. 모니터링 대시보드 명세

## 목표

스케일링 전/후 트래픽 결과를 **실측값으로** 보여주고, 그 결과를 발표 증빙으로 남긴다.

두 개의 화면을 역할별로 나눈다.
- **Grafana**: 부하 테스트 중 실시간 인프라 상태 (TPS, P95, 에러율, replica 수)
- **InfraGuard UI 결과 패널**: 라운드별 측정 결과 비교 (진단 → 스케일링 → 재측정)

## 금지 사항

- 목업/샘플/랜덤 데이터로 차트를 채우지 않는다. 데이터가 없으면 "측정값 없음"을 표시한다.
- 외부 CDN을 쓰지 않는다 (시연장 네트워크 리스크). 차트 라이브러리가 필요하면 `backend/app/static/vendor/`에 파일로 포함하거나, 의존성 없는 SVG로 구현한다.
- `schemas.py`, `state.py`의 기존 필드와 `/report`의 기존 응답 필드는 변경·삭제하지 않는다.
- 가드레일 값(01_개발계획.md)을 바꾸지 않는다.

## 우선순위

13:00 마감 기준 **Phase 1~4 필수**, Phase 5는 시간이 남으면 진행한다.
Phase마다 완료 기준을 직접 확인하고 커밋한 뒤 다음 Phase로 넘어간다.

## Phase 2. 로드밸런서 추가 (ISSUE-1)

**선행 확인:** Phase 1 완료 후 replica 3개 상태에서 기존 방식대로 부하를 주고
`sum by (instance) (rate(http_requests_total[1m]))`로 분산 여부를 먼저 기록한다 (02_알려진이슈.md ISSUE-1).

**작업**
- `docker-compose.yml`에 nginx 서비스 추가. target-server replica들로 요청을 분산한다.
- 스케일 후 새 replica가 nginx에 반영되는 방식을 정하고, 그 근거를 PR 설명에 적는다.
  (예: Docker DNS resolver `127.0.0.11` + 변수 proxy_pass 방식, 또는 스케일 후 nginx reload)
- 포트 (구현 기준으로 정정): target-server의 호스트 포트 매핑(`8080-8089`)을 없애고 nginx가 호스트 8080을 고정으로 받는다.
  범위 매핑이 사라지므로 포트 겹침(Locust 웹 UI 8089 포함)이 없어지고, 재생성 후 8080이 비는 문제(ISSUE-9)도 함께 해결된다.
- 부하 대상 주소 (구현 기준으로 정정): nginx가 8080을 받으므로 `.env.example`의 `TARGET_SERVER_URL`,
  `infra/locust/locust.conf`의 `host`, `run_load_test.py` 기본값(`http://localhost:8080`)은 바꾸지 않는다.
  `docker-compose.yml` backend 환경변수만 `http://nginx:8080`으로 바꾼다.
  **주의: locust.conf는 ASCII만 허용** (한글 주석 넣으면 Windows에서 크래시 — 파일 내 NOTE 참고).
- 새 replica 반영 (구현): nginx upstream `server target-server:8080 resolve` (오픈소스 1.27.3+, `nginx:1.28-alpine`),
  `resolver 127.0.0.11 valid=2s`. 근거는 `infra/nginx/nginx.conf` 주석.
- 스케일 직후 재측정에 기동 중 replica가 섞이지 않도록 `scale_service`가 `docker compose up --wait`로 healthy까지 기다린다.
- Prometheus는 nginx가 아니라 replica를 직접 수집한다 (Phase 1 설정 유지).
- README의 포트/실행 안내 갱신.

**완료 기준**
- [x] replica 3개에서 부하 테스트 시 `sum by (instance)(rate(http_requests_total[1m]))`로 3개 replica 모두 요청 수신 확인
  (2026-09-11: 32.48 / 32.07 / 32.31 req/s, 02_알려진이슈.md ISSUE-1)
- [x] replica 1 → 3 스케일 직후에도 새 replica로 요청이 들어감 (scale_service 반환 후 10~15초에 수신 관측, ISSUE-1)

## Phase 4. UI 결과 비교 패널

**작업** (`backend/app/static/`)
- 리포트 단계에서 결과 패널 표시:
  - 비교 카드: 스케일링 전/후 TPS, P95, 에러율, replica 수와 변화량 (값이 나빠졌으면 나빠진 대로 표시)
  - 라운드별 차트: x축 round, TPS와 P95 추이, replica 수 표기
  - 측정 조건 표시: 동시 가상 사용자 수(target_tps), duration, replica 수
  - target_tps는 "목표 TPS"가 아니라 **"동시 가상 사용자 수"로 표기**한다. `run_load_test.py`가 target_tps를
    Locust `--users`로 넘기므로 처리량 목표가 아니다 (02_알려진이슈.md ISSUE-11). 처리량(TPS)은 측정값 `tps`만 쓴다.
- 데이터 출처는 `/report`만 사용한다. (구현 기준으로 정정: `measurement_history`만으로는 AI 판단 카드·측정 조건을 그릴 수 없어
  Phase 4에서 추가한 `/report` 필드도 쓴다. 아래 "구현")
- Grafana 대시보드로 가는 링크 버튼 (http://localhost:3000).
- 기존 로그 출력과 진행 단계 표시는 유지한다.

**구현** (코드 기준, #75 — `backend/app/static/result_panel.js`, 브랜치 `feature/75-result-panel`)
- `/report` 추가 필드(결과 파일과 같은 값, 기존 필드 유지): `conditions`, `end_reason`, `user_decision`, `diagnoses`, `approvals`,
  `scaling_results`, `revalidations`. #83 게이트 필드는 `low_confidence`, `low_confidence_threshold`다(02 ISSUE-13).
- 패널은 리포트 단계에서 진행 바와 로그 사이에 나온다.
  1. 한 줄 요약 배너 — 측정값 템플릿이다(LLM 문장 아님). end_reason별 문구:
     - 스케일링 완료: `P95 a → b · SLO … · 서버 x→y대`. 재진단에서 추가 제안이 없으면 끝에 `· 재진단: 추가 스케일링 미제안`.
     - 미제안: SLO 충족이면 `스케일링 불필요 판단 · …`, 미충족·경계면 `스케일링 미제안 · …`. AI 판단 카드의 결론 배지도 같은 규칙이다
       (충족일 때만 "스케일링 불필요", 아니면 "스케일링 미제안").
     - 거절: `스케일링 제안(x→y대) 거절 · …`. 실패: `실행 실패 · …`.
  2. AI 판단 카드 — 최초 진단의 결론 배지(forced면 "LLM 판단: 스케일링 불필요 → 디버그로 강제 승인 요청"), 심각도, 신뢰도 막대(60% 기준선),
     진단 입력 측정값 칩(P95 vs SLO 배수, 활성 연결, 에러율, TPS), "판단 제외: CPU·메모리(측정 불가)" 칩, 사용자 결정.
     LLM 원문(cause, recommendation, 재검증 summary)은 접어서 보여준다. 이후 라운드는 재검증 → 재진단 순서로 아래에 붙는다.
  3. 전/후 비교 — 첫 라운드와 마지막 라운드 카드(TPS, P95, 에러율, 서버 수와 변화량. 나빠진 값도 그대로). 라운드가 1개면 단일 측정 카드와 사유.
     라운드별 P95(SLO 점선 기준선)·TPS 막대 차트를 둔다. 중간 라운드는 차트 추이로만 보인다.
  4. 측정 조건 — 동시 가상 사용자 N명, 부하 시간, P95 SLO, 시작 서버 수, LLM 모델, 결과 파일, 코드 버전.
     forced_scaling이면 "디버그 강제 실행 — 발표 수치 아님" 경고가 뜬다.
  5. Grafana 링크 버튼. Phase 5(#74)부터 프로비저닝·익명 보기 전용·홈 대시보드 지정으로, 누르면 로그인 없이 대시보드가 바로 뜬다(02 ISSUE-4).
     (Phase 4 당시에는 프로비저닝이 없어 수동 import가 필요했다.)
- SLO 판정: P95 < SLO 충족(초록), P95 = SLO 경계(= SLO)(노랑), P95 > SLO 미충족(빨강).
  Locust 반올림 때문에 SLO와 같은 기록값은 실제로는 SLO를 넘었을 수 있다(02 ISSUE-10 관찰 2).
- 자릿수: TPS 소수 1자리, P95 정수 ms, 에러율 % 소수 2자리. 변화량은 원본값으로 계산한 뒤 표시 자릿수로 반올림한다(0이면 "변화 없음").
- 차트는 외부 라이브러리 없이 inline SVG로 그린다. LLM 문자열은 textContent로만 넣는다. 값이 없으면 "측정값 없음"을 표시한다.
- 서버 수 표시·1대 초기화: 입력 영역에 "현재 서버 N대"(`GET /api/v1/agent/replicas`, docker compose 실제 값, 실행이 끝날 때마다 갱신)와
  "서버 1대로 초기화" 버튼(`POST /api/v1/agent/replicas/reset` → `scale_service(1)`, 확인 대화상자)을 둔다.
  에이전트 실행 중·승인 대기 중·초기화 중이면 버튼이 비활성화되고 서버도 409로 거부한다.

## 발표용 측정 절차 (Phase 4 완료 후)

1. 측정 조건 고정: PC 사양 기록, target_tps / duration 고정, 시작 replica 1
2. 같은 조건으로 **3회 이상** 반복 실행 → `results/` 파일 전부 보관
3. 발표에는 반복 결과의 범위 또는 중앙값을 쓰고, 측정 조건을 슬라이드에 함께 적는다
4. 개선이 작거나 없으면 그대로 보고하고 원인을 분석한다. 수치를 조정하지 않는다.
5. 측정 전에 코드를 커밋하고 uvicorn을 재시작한다. 결과 파일의 `code_version`은 서버가 코드를 읽은 시점의 값이다.
   재시작하지 않으면 커밋 전 해시와 `code_dirty=true`가 기록된다 (02_알려진이슈.md ISSUE-5).
6. **측정 중 브라우저(UI 탭)를 닫거나 새로고침하지 않는다.** 부하 테스트 중 연결이 끊기면 SSE는 끝나지만 Locust 서브프로세스는
   계속 돌 수 있다. 다음 회차와 겹치면 측정이 오염된다 (02_알려진이슈.md ISSUE-5, 204627 / 233316 R1).
   - 동시 실행 방지 (02 ISSUE-17): 다른 실행이 진행 중(승인 대기 포함)이거나 끊긴 실행의 Locust가 아직 돌면
     시작 버튼과 "서버 1대로 초기화" 버튼이 막히고, 서버도 409로 거부한다. 막힌 이유는 입력 영역에 표시된다.
   - 끊긴 실행의 Locust는 강제로 끝내지 않는다. 끝나면(늦어도 부하 시간 + 60초) 버튼이 다시 켜진다.
   - 여러 탭에서 동시에 열어 두지 않는다. 막히긴 하지만 어느 탭의 실행인지 헷갈린다.
7. 회차마다 시작 전에 "서버 1대로 초기화"를 누르고 "현재 서버 1대"를 확인한다. 초기화는 results/에 기록되지 않는다.
