## ISSUE-1 [치명] 스케일 아웃해도 부하가 새 replica로 분산되지 않을 가능성

**코드에서 확인된 사실**
- `docker-compose.yml`: target-server가 `ports: "8080-8089:8080"`로 replica마다 호스트 포트를 하나씩 받는다.
  앞단에 로드밸런서(nginx 등)가 없다.
- `infra/locust/locust.conf`: `host = http://localhost:8080`
- `backend/app/tools/run_load_test.py`: `DEFAULT_HOST = os.getenv("TARGET_SERVER_URL", "http://localhost:8080")`
- 백엔드를 호스트에서 uvicorn으로 실행하면 부하는 `localhost:8080` = **replica 1개**로만 간다.
- 백엔드를 `--profile app` 컨테이너로 실행하면 `http://target-server:8080`(Docker DNS)을 쓰는데,
  분산은 클라이언트의 DNS 해석·keep-alive 동작에 좌우되어 균등하다는 보장이 없다.

**영향**
스케일링 전/후 비교가 "replica 증가 효과"를 측정하지 못한다.
전/후 수치 차이가 나와도 스케일링 효과인지 측정 노이즈인지 구분할 수 없다.

**실행으로 확인할 것** (ISSUE-2 해결 후 가능)
1. `docker compose up -d --scale target-server=3`
2. 평소 실행 방식 그대로 부하 테스트 실행
3. Prometheus에서 `sum by (instance) (rate(http_requests_total[1m]))` → replica별 요청이 고르게 들어오는가?

**해결 방향:** target-server 앞에 nginx 로드밸런서 서비스 추가, 부하는 nginx로 보낸다. (03_대시보드명세.md Phase 2)

## ISSUE-2 [높음] Prometheus가 replica 1개만 수집

**코드에서 확인된 사실**
- `infra/prometheus/prometheus.yml`: `static_configs: targets: ["target-server:8080"]` 단일 타깃.
  파일 주석에도 스케일 후 과소집계 문제와 `dns_sd_configs` 해결책이 적혀 있다.
- `backend/app/tools/get_metrics.py`: `sum(http_requests_in_progress) or vector(0)` → 1개 replica 값만 합산됨.

**영향:** 스케일 후 Grafana TPS/P95/connection 수치가 실제보다 작거나 왜곡된다.

**해결 방향:** `dns_sd_configs`(names: target-server, type: A, port: 8080)로 교체.

## ISSUE-3 [중간] Windows Docker Desktop에서 cAdvisor 패널이 비어 있음

**코드에서 확인된 사실**
- `infra/grafana/dashboard.json`의 CPU/메모리/Replica 패널이 `name=~"infraguard-target-server.*"` 라벨을 사용.
- 일일보고 Day3: Windows에서 cAdvisor `name` 라벨 미지원 확인 → `get_metrics.py`의 cpu_pct/mem_pct는 0.0 고정.

**해결 방향**
- Replica 수: `count(up{job="target-server"} == 1)`로 대체 (ISSUE-2 해결 후 동작).
- CPU/메모리: 시연 PC OS에서 실제로 값이 나오는지 확인 후 유지/제거 결정. 값이 안 나오는 패널은 발표 화면에 두지 않는다.

## ISSUE-4 [중간] Grafana 프로비저닝 없음

**코드에서 확인된 사실**
- `docker-compose.yml`: `./infra/grafana`를 `/var/lib/grafana/dashboards`에 마운트만 한다.
  datasource / dashboard provider 프로비저닝 파일이 없다.
- `dashboard.json`의 모든 패널은 datasource `uid: "prometheus"`를 참조한다.

**영향:** 새 환경에서 `docker compose up` 후 데이터소스와 대시보드를 수동으로 만들어야 한다. 시연 중 실수 위험.

**해결 방향:** `infra/grafana/provisioning/{datasources,dashboards}/` 추가, datasource uid를 `prometheus`로 고정.

## ISSUE-5 [낮음] 측정 이력이 메모리에만 있고 1회분만 보관

**코드에서 확인된 사실**
- `backend/app/api/v1/agent.py`: `before_measurements[task_id]`에 스케일링 전 값을 **최초 1회만** 저장.
  이후 `state["load_test_result"]`는 재검증 값으로 덮어써진다.
- 다회차 스케일링 시 중간 라운드 측정값은 사라진다. 서버 재시작 시 전부 사라진다.
- UI(`static/main.js`)는 `/report`의 전/후 값을 **로그 텍스트로만** 출력한다.

**영향:** 발표용 실측 증빙을 남길 수 없고, 라운드별 추이를 시각화할 수 없다.

**해결 방향:** 라운드별 측정 이력 누적 + JSON 파일 저장 + UI 비교 차트. (03_대시보드명세.md Phase 3~4)
