## ISSUE-1 [치명] 스케일 아웃해도 부하가 새 replica로 분산되지 않을 가능성

**코드에서 확인된 사실**
- `docker-compose.yml`: target-server가 `ports: "8080-8089:8080"`로 replica마다 호스트 포트를 하나씩 받는다.
  앞단에 로드밸런서(nginx 등)가 없다.
- `infra/locust/locust.conf`: `host = http://localhost:8080`
- `backend/app/tools/run_load_test.py`: `DEFAULT_HOST = os.getenv("TARGET_SERVER_URL", "http://localhost:8080")`
- 백엔드를 호스트에서 uvicorn으로 실행하면 부하는 `localhost:8080` = **replica 1개**로만 간다.
- 백엔드를 `--profile app` 컨테이너로 실행하면 `http://target-server:8080`(Docker DNS)을 쓰는데,
  분산은 클라이언트의 DNS 해석·keep-alive 동작에 좌우되어 균등하다는 보장이 없다.

**영향**
스케일링 전/후 비교가 "replica 증가 효과"를 측정하지 못한다.
전/후 수치 차이가 나와도 스케일링 효과인지 측정 노이즈인지 구분할 수 없다.

**실행으로 확인할 것** (ISSUE-2 해결 후 가능)
1. `docker compose up -d --scale target-server=3`
2. 평소 실행 방식 그대로 부하 테스트 실행
3. Prometheus에서 `sum by (instance) (rate(http_requests_total[1m]))` → replica별 요청이 고르게 들어오는가?

**해결 방향:** target-server 앞에 nginx 로드밸런서 서비스 추가, 부하는 nginx로 보낸다. (03_대시보드명세.md Phase 2)

- [x] 실행 확인 결과 (2026-09-11, Phase 1 적용 후):
  - 조건: replica 3개, Locust 50 users 60초, `--host http://localhost:8084` (replica 1개의 호스트 포트.
    재생성 후 8080이 비어 있어 이 포트를 썼다 → ISSUE-9)
  - `sum by (instance) (rate(http_requests_total[1m]))`: `172.18.0.3` 하나만 약 47 req/s, 나머지 2개는 0
  - Locust: 2829 req, 47.49 req/s, 실패 0.42% (`/flaky`만 5.41%), `/heavy` P95 3200ms, 평균 2557ms
  - 결론: replica를 늘려도 부하는 1개로만 간다. **이 수치는 발표용 before 값이 아니라 ISSUE-1 증거로만 쓴다.**

**Phase 2 적용** (코드): target-server 앞에 nginx 로드밸런서를 추가했다(`infra/nginx/nginx.conf`, `docker-compose.yml`).
부하는 `localhost:8080`(호스트) / `nginx:8080`(컨테이너 네트워크) → nginx → replica 라운드로빈으로 간다.
backend 컨테이너의 `TARGET_SERVER_URL`도 `http://nginx:8080`으로 바꿔 호스트 실행과 같은 경로로 측정한다.
Phase 2 이전 수치(replica 직결)는 nginx를 거치는 이후 수치와 비교 대상이 아니다.

- [x] Phase 2 적용 후 실행 확인 (2026-09-11):
  - 분산: replica 3개, Locust 50 users 60초(`locust.conf` host `localhost:8080` = nginx).
    `sum by (instance) (rate(http_requests_total[1m]))`(부하 종료 직전): `172.18.0.7` 32.48 / `172.18.0.3` 32.07 / `172.18.0.6` 32.31 req/s.
    3개 모두 요청을 받았고 거의 균등하다.
    Locust: 6447건, 108.20 req/s, 실패 0.47%(`/flaky` 500 30건뿐), `/heavy` 평균 476ms, P95 770ms.
  - 1→3 스케일 직후: 부하(50 users) 중 `scale_service(3)` 호출 → 7.6초 후 반환(`--wait` 포함, before 1 → after 3).
    `rate(...[15s])` 기준으로 새 replica는 반환 후 10~15초에 요청 수신이 관측됐고, 20초 후에는 3개가 약 38 req/s씩 균등했다.
    관측 지연에는 Prometheus dns_sd 갱신(5s) + scrape(5s) + rate 창이 포함된다.
  - 부하 중 scale-down(3→1) 순간: 100초 실행 8405건 중 `/flaky` 500 46건 외에 `/light` 504가 1건 있었다
    (약 2000ms, nginx 로그 `upstream timed out while connecting to upstream`). 제거되는 replica로 가던 요청이다.
    에이전트 흐름은 부하 테스트가 끝난 뒤 스케일링하므로 측정 중에는 scale-down이 일어나지 않는다.
    이 100초 실행의 `/heavy` P95(3100ms)는 replica 1개 구간이 섞인 값이라 비교용이 아니다.
  - 위 수치는 nginx 경유 조건의 검증 기록이며 발표용 before/after 값이 아니다.
  - UI 흐름 (DEBUG 꺼짐, replica 1, target_tps 50): 진단은 정상 완료됐다(TPS 60.6, P95 2800ms, 활성 연결 37).
    LLM은 스케일링 불필요로 판단했다. 진단 문구의 "CPU/메모리 0%로 자원 병목 없음"은 고정값(ISSUE-3)이
    LLM 입력에 들어간 결과다 → #78(ISSUE-10)에서 처리한다.
  - 스케일링 경로 기계 검증 (`DEBUG_ENDPOINTS_ENABLED=true` + `force_scaling`, 검증 후 즉시 끔):
    승인 모달 → 1→2 스케일 → 재측정 → 리포트까지 정상 동작했다. 승인부터 재측정 완료까지 약 34초(재측정 부하 10초 포함).
    강제 실행이므로 이 실행의 측정값은 기록하지 않는다.

## ISSUE-2 [높음] Prometheus가 replica 1개만 수집 — Phase 1 해결

**코드에서 확인된 사실**
- `infra/prometheus/prometheus.yml`: `static_configs: targets: ["target-server:8080"]` 단일 타깃.
  파일 주석에도 스케일 후 과소집계 문제와 `dns_sd_configs` 해결책이 적혀 있다.
- `backend/app/tools/get_metrics.py`: `sum(http_requests_in_progress) or vector(0)` → 1개 replica 값만 합산됨.

**영향:** 스케일 후 Grafana TPS/P95/connection 수치가 실제보다 작거나 왜곡된다.
(connection 수는 ISSUE-6 때문에 수정 전에는 항상 0이었다.)

**해결 방향:** `dns_sd_configs`(names: target-server, type: A, port: 8080)로 교체.

**Phase 1 적용:** `prometheus.yml`의 target-server job을 `dns_sd_configs`
(names: `target-server`, type: `A`, port: `8080`, refresh_interval: `5s`)로 교체했다.
`get_metrics.py` 쿼리는 바꾸지 않았다. `sum(...)`이 디스커버리된 타깃 전체를 합산한다.

- [x] 실행 확인 결과 (2026-09-11, replica 3):
  - `promtool check config`: SUCCESS
  - `/targets`: target-server 3/3 UP (instance `172.18.0.3` / `172.18.0.6` / `172.18.0.7` `:8080`)
  - `count(up{job="target-server"} == 1)` = 3
  - [x] scale 1로 줄인 뒤 결과 (2026-09-11 Phase 2 검증): 부하 중(Locust 50 users, nginx 경유) `scale_service(1)` 호출 → 4.0초 후 반환
    (`before_replicas=3, after_replicas=1, success=True`). 반환 5초 뒤 조회에서는 아직 3, 10초 뒤 `count(up{job="target-server"} == 1)` = 1.
    `sum by (instance) (rate(http_requests_total[15s]))`도 instance 1개(`172.18.0.3`)만 남았다.

  `histogram_quantile(0.95, sum by (handler, le) (rate(http_request_duration_seconds_bucket[1m]))) * 1000`
- 라이브러리 `metrics.default()`의 `http_request_duration_seconds` 히스토그램은 `latency_lowr_buckets=(0.1, 0.5, 1)`을 쓴다.
- Prometheus 공식 문서(`histogram_quantile`): quantile이 최상위 버킷(+Inf)에 있으면 두 번째로 높은 버킷의 상한을 반환하고,
  버킷 안에서는 선형보간한다.

**수정 전 런타임 확인** (예전 이미지, 재빌드 전)
- `http_request_duration_seconds_bucket`의 `le` = `0.1`, `0.5`, `1.0`, `+Inf`

**영향:** 실제 P95가 1s를 넘어도 패널에는 1000ms로 표시된다. 0.1~1s 구간도 버킷 3개 사이 선형보간이라 정밀도가 낮다.
- 참고: ISSUE-1 실행에서 Locust가 잰 `/heavy` P95는 3200ms였다. 이 구간에서 Grafana P95 패널은 1000ms로 잘려 보일 것으로 예상된다(패널 표시는 미확인).

**해결 방향:** Phase 5에서 처리한다. 이번 Phase에서는 코드를 수정하지 않는다.
발표용 P95는 Locust 측정값(`LoadTestResult.latency_p95`)을 쓴다.

## ISSUE-11 [중간] target_tps가 처리량이 아니라 동시 가상 사용자 수로 쓰임 — "50 TPS 상한"은 "동시 가상 사용자 50 상한"

**코드에서 확인된 사실**
- `backend/app/tools/run_load_test.py`: `target_tps`를 Locust `--users`(동시 가상 사용자 수)와 `--spawn-rate`로 넘긴다.
  `MAX_TPS = 50`은 이 users 값의 상한이다. 처리량 자체를 제한하는 설정(예: `constant_throughput` wait_time)은 없다.
- `infra/locust/locustfile.py`: `wait_time = between(0.1, 0.5)`. 가상 사용자 1명의 초당 요청 수는 대기 시간과 응답 시간에 따라 달라진다.
- 주석 `infra/locust/locust.conf` "Each virtual user maps to roughly 1 TPS", `run_load_test.py` "가상 사용자 수(≈TPS)"는 아래 실측과 맞지 않는다.
- "목표 TPS" 표기: UI 입력 라벨(`backend/app/static/index.html`), LLM 프롬프트(`prompts.py` "[사용자가 요청한 목표 TPS]", "목표 TPS를 실제로 달성했는지"),

## ISSUE-16 [중간] run_load_test가 Locust 출력을 cp949로 읽어 디코딩 실패, 요청 0건 결과를 정상 반환 — #84

**실행으로 확인한 사실** (2026-09-11, 로컬, 사용자 인프라 미사용)
- `run_load_test(target_tps=1, duration=3, host="http://127.0.0.1:9")`(닫힌 포트)를 실행하자 백엔드 콘솔에
  `Exception in thread Thread-2 (_readerthread)` … `UnicodeDecodeError: 'cp949' codec can't decode byte 0xeb in position 2671`이 남았다.
  예외는 subprocess 출력 읽기 스레드에서 났고 `run_load_test`는 예외 없이 반환했다. 읽지 못한 Locust 출력은 버려진다.
- 같은 실행이 `LoadTestResult(tps=0.0, latency_p95=0.0, latency_avg=0.0, error_rate=0.0, duration=3, total_requests=0)`로 정상 반환됐다.
- 처음 본 것은 #75 locustfile 훅 스모크 테스트였다. 같은 방식(`text=True`)으로 Locust를 실행한 스크립트에서도 같은 예외가 났다.

**코드에서 확인된 사실**
- `backend/app/tools/run_load_test.py`: `subprocess.Popen(..., stdout=PIPE, stderr=PIPE, text=True)`로 인코딩을 지정하지 않아
  Windows 한국어 환경에서 시스템 코드페이지(cp949)로 디코딩한다.
- 0xEB는 UTF-8 한글의 첫 바이트다. 연결 거부 시 Windows 한국어 오류 메시지가 Locust 출력에 들어가는 것으로 추정한다(미확인).

**영향**
- target-server에 연결할 수 없을 때처럼 Locust 오류 출력이 가장 필요한 상황에서 stderr가 사라진다.
- 요청 0건 결과가 측정값처럼 LLM 진단에 전달될 수 있다. ISSUE-9(연결 실패가 측정값으로 전달)와 같은 종류라 처리 방향은 별도로 정한다.
- 연결이 정상인 부하에서는 이번 Phase 3·4 실행 모두 결과를 문제없이 받았다.
- #75 범위 밖이라 이번 브랜치에서는 고치지 않는다. gh 이슈 **#84** (2026-09-11 등록, 라벨 bug).

## ISSUE-17 [높음] 동시 실행으로 측정 오염 — 실행 중이거나 끊긴 실행의 Locust가 남아 있어도 새 실행 가능 — #87

**실행으로 확인한 사실** (2026-09-11, ISSUE-5 Phase 4 그래프 UI 실행 확인 4번)
- 실행 3개가 16초 안에 시작됐다.
  - 233300 (동시 가상 사용자 50, 23:33:00 시작, 승인 대기 중 23:33:44 stream_closed)
  - 233310 (30, 23:33:10 시작, 부하 테스트 중 23:33:12 stream_closed)
  - 233316 (50, 23:33:16 시작). 233300이 승인을 기다리는 동안 시작됐다.
- 233316 R1의 서버별 요청 합은 533건인데 이 실행의 Locust는 314건이었다(Prometheus /light 567 vs 217).
  233310의 Locust가 스트림이 끊긴 뒤에도 돌아 R1이 오염됐다(TPS 39.1 / P95 4800ms, 발표 수치에서 제외).

**코드에서 확인된 사실** (수정 전)
- `/api/v1/agent/start`는 다른 실행이 진행 중이어도 새 실행을 시작했다. 시작 버튼은 같은 탭 안에서만 막혔다.
- 부하 테스트는 `asyncio.to_thread`로 Locust 서브프로세스를 실행한다. 스트림이 끊겨 코루틴이 취소돼도 스레드와 Locust는 끝까지 돈다.
  `run_load_test`는 `communicate(timeout=duration + 60)`을 넘기면 프로세스를 끝낸다.

**수정** (#87, 브랜치 `fix/measurement-accuracy`)
- `agent.py` `LoadTestTracker`(`load_tests`): 부하 테스트 스레드가 시작하면 task별로 세고, 스레드가 끝나면 뺀다(스트림이 끊겨도 스레드가 끝날 때 뺀다).
- 새 실행을 막는 이유 `_busy_reason()`:
  - `agent_running`: finalize되지 않은 기록기가 있다(실행 중·승인 대기)
  - `load_test_running`: 끝나지 않은 부하 테스트 스레드가 있다
  - `replica_reset`: 서버 수 초기화 중이다
- `GET /agent/start`는 이유가 있으면 409다. 확인과 스트림 시작 사이에 끼어든 요청은 스트림 첫 이벤트에서 한 번 더 거부한다.
  이 확인부터 기록기 등록까지는 await가 없어 이벤트 루프 안에서 한 번에 처리된다. 거부된 요청은 결과 파일을 만들지 않는다.
- `POST /agent/replicas/reset`도 실행 중·부하 테스트 대기 중이면 409다. `GET /agent/replicas`에 `busy_reason`을 추가했다(필드 추가).
- UI: 서버가 busy면 시작·초기화 버튼을 막고 이유를 입력 영역에 표시한다. busy인 동안 3초마다 다시 확인해 풀리면 버튼을 켠다.
  시작 버튼을 누른 직후에도 한 번 더 확인한다.
- 끊긴 실행의 Locust는 **강제로 끝내지 않고, 끝날 때까지 새 실행을 막는다.** 근거:
  - 스레드는 이미 스스로 끝나고, `run_load_test` 타임아웃(부하 시간 + 60초)이 기다리는 시간의 상한이다.
  - 강제로 끝내려면 실행 중인 프로세스를 따로 추적해 다른 스레드에서 kill해야 한다. 결과 파싱·임시 디렉터리 정리와 경합하고,
    다른 실행의 프로세스를 잘못 끝낼 위험을 새로 만든다. 기다리는 쪽은 기존 부하 테스트 코드를 바꾸지 않는다.
  - 기다리는 동안 새 측정이 시작되지 않으므로 오염을 막는 목적은 같다.

**검증** — 단위 테스트 (`tests/unit/test_run_gate.py`)
- 실행 중(기록기 미종료)이면 `/agent/start` 409.
- 끝나지 않은 부하 테스트 스레드가 있으면 시작·초기화 409, `busy_reason=load_test_running`. 스레드가 끝나면 다시 허용.
- start_agent 확인 뒤에 다른 실행이 먼저 시작된 경우: 스트림 첫 이벤트에서 거부하고 결과 파일을 만들지 않음.
- 부하 테스트 중 스트림을 취소하면 결과 파일은 `stream_closed`로 저장되고, 멈춰 둔 Locust 스레드가 끝날 때까지 시작·초기화 409 → 끝나면 허용.
- 실측 재검증은 대기 중이다.
