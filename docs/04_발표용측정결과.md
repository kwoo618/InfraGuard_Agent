## 6. 관찰

### 관찰 1. 30초 측정에서 2대 P95가 SLO를 일관되게 넘었다

- 30초: 2대 3라운드의 P95는 1100 / 1200 / 1200ms로 모두 SLO를 넘었다.
  Locust 반올림(1000ms 이상은 100ms 단위)을 감안해도 1100은 1050ms 이상 구간이라 초과 판단은 바뀌지 않는다.
- 이전 10초 측정의 2대 P95(`02_알려진이슈.md`): 980 (ISSUE-10 1회), 1000 (ISSUE-10 2회), 1000 (Phase 3 204454), 980 (Phase 4 221638), 1200 (Phase 4 233316 R2).
  5라운드 중 4라운드가 980~1000ms 경계였고, 1라운드는 1200ms였다.
  10초 측정은 코드 버전과 헤드라인 계산 방식(수정 전 `_stats.csv`, 마지막 약 1초 제외)이 달라 직접 비교에는 한계가 있다.
- 30초 2대 라운드의 초별 P95 (그래프 ①, 요청별 원시 응답시간의 nearest-rank P95):

| 라운드 | 0~9초: 1000ms 넘은 초 / 초별 P95 중앙값 | 10~29초: 1000ms 넘은 초 / 초별 P95 중앙값 | 헤드라인 P95 |
|---|---|---|---|
| 005245 R2 | 5 / 10초, 973ms | 9 / 20초, 951ms | 1100 |
| 005555 R2 | 6 / 10초, 1028ms | 15 / 20초, 1216ms | 1200 |
| 005741 R2 | 4 / 10초, 936ms | 16 / 20초, 1332ms | 1200 |

  - 005555·005741은 뒤 20초의 초별 P95가 더 높았다. 005245는 앞뒤가 비슷했다.
  - 앞 10초만 보면 경계 근처였을 수 있다(추정). 10초 측정이 경계값으로 나온 이유가 이것인지는 확인하지 않았다.
- 1대는 5회 모두 30초 중 29초가 1000ms를 넘었다. 4대는 한 번도 넘지 않았다(0 / 30초, 초별 P95 최대 621ms).
- 발표에서 30초 기준으로 "2대로 SLO 충족"이라고 말할 수 없다. SLO를 충족한 구성은 4대(2 / 2)다.

### 관찰 2. 한 실행 안에서 재검증 LLM과 재진단 LLM의 판단이 어긋났다

흐름(`backend/app/agent/engine.py`): 스케일 후 재측정 → 재검증 LLM(전/후 비교) → `additional_action_required=true`면 재측정값으로 재진단 LLM →
스케일링 여부는 재진단의 `requires_scaling`만으로 정해진다. 최종 메시지는 재검증 요약·추가 권장 조치 뒤에 재진단 결과를 붙인다.

- **005555** (재검증은 추가 스케일링을 권했고, 재진단은 제안하지 않았다):
  - R2 재검증: `additional_action_required=true`, 추가 권장 조치 "…애플리케이션 최적화(쿼리 튜닝, 캐싱 등) 또는 추가 스케일링이 필요합니다. 현재 컨테이너 수를 2배 증가시킨 후 재측정을 권장합니다."
  - R2 재진단: `requires_scaling=false` (medium / 85%), 권장 조치 "…3. 컨테이너 스케일링 전 추가 진단 수행" → `no_further_scaling`으로 종료(P95 1200ms, SLO 미충족).
  - 최종 메시지(`final_message`)에 두 문구가 이어서 들어간다("…2배 증가시킨 후 재측정을 권장합니다. 진단 완료: …").
- 반대 방향도 있었다. **005245** R2 재검증의 추가 권장 조치는 "…현재 컨테이너 수를 유지하면서 애플리케이션 로그 및 외부 종속성 모니터링을 권장합니다."였는데,
  재진단은 2→4를 제안했다(medium / 85%).
- 두 호출은 프롬프트와 출력 형식이 다른 별도 LLM 호출이다. 재진단 프롬프트(`build_bottleneck_analysis_prompt`)의 입력은 재측정값·메트릭·현재 서버 수이고
  재검증 결과는 들어가지 않는다. 그래서 재검증의 추가 권장 조치 문구는 스케일링 판단에 쓰이지 않는다.
  대회 이후 개선 과제로 둔다. 이번에는 코드·프롬프트를 바꾸지 않았다.

### 관찰 3. "활성 연결 수 < 동시 사용자 수 → 병목 가능성 낮음"으로 해석하는 패턴

활성 연결 수(`connection_count`)는 부하 테스트가 끝난 뒤 Prometheus에서 조회한 `sum(http_requests_in_progress)`,
즉 target-server 전체에서 처리 중이거나 대기 중인 요청 수의 순간값이다(`backend/app/tools/get_metrics.py`).

| 회차·라운드 | 활성 연결 / 동시 사용자 | LLM 문구 (cause) | 판단 |
|---|---|---|---|
| 005124 R1 | 35 / 50 | "활성 연결 수(35)가 동시 가상 사용자 수(50)보다 현저히 낮아 네트워크 병목 가능성은 낮습니다" … "컨테이너 스케일링만으로는 해결되지 않을 가능성이 높습니다" | 미제안 |
| 005555 R2 | 19 / 50 | "활성 연결 수(19)는 현재 부하(50 VUs)에 비해 낮아 네트워크 병목 가능성은 낮습니다" | 미제안 |
| 005741 R2 | 22 / 50 | "활성 연결 수(22)는 현재 부하(50 VUs) 대비 낮아 연결 수 자체가 병목 원인으로 보이지 않습니다" | 2→4 제안 |

- 같은 지표를 반대로 읽은 문구도 있다: "활성 연결 수(35)가 현재 단일 컨테이너에서 처리 가능한 수준을 초과할 가능성"(005245 R1),
  "(37)가 현재 컨테이너 수(1) 대비 과부하 상태일 가능성"(005741 R1), "(20)가 현재 컨테이너 수(2) 대비 10개 연결/컨테이너 … 병목이 발생할 수 있는 수준"(005245 R2).
- 가상 사용자는 요청 사이에 0.1~0.5초씩 쉬므로 50명이 늘 동시에 요청 중인 것은 아니다. P95가 3000ms대인 1대에서도 활성 연결 수는 34~37로 50보다 적었다.
  활성 연결 수가 동시 사용자 수보다 적다는 것은 병목이 있어도 나오는 값이라, 둘을 비교해 병목 가능성을 낮게 보는 해석은 근거가 약하다.
- 프롬프트는 고치지 않았다(결과를 보고 프롬프트를 고치지 않는다, 02 ISSUE-10 관찰 1).
  대회 이후 개선 과제: 진단 입력에 활성 연결 수의 뜻(서버 안에서 처리·대기 중인 요청 수의 순간값, 동시 사용자 수와 직접 비교할 수 없음)을 적는다.

### 관찰 4. LLM 요약 문구의 수치가 측정값과 다른 경우가 있었다

- 005245 R2 재검증 요약은 "TPS는 47.09에서 94.03으로 증가"라고 적었다. 결과 파일의 측정값은 47.29 → 94.32다. 같은 문장의 P95(3100 → 1100)와 에러율은 측정값과 같다.
- 나머지 회차의 재검증 요약 수치는 측정값과 같았다. 결과 패널의 비교 카드·그래프는 LLM 문구가 아니라 측정값으로 그린다.

## 7. 대표 사례 추천: `005741`

2회 루프(1→2→4)로 SLO를 충족한 회차는 005245와 005741 두 개다. **005741**을 추천한다.

추천 이유:
1. 결과 패널에 보이는 LLM 문구의 수치가 모두 결과 파일 측정값과 같다. 발표 화면의 숫자를 그대로 설명할 수 있다.
2. 재검증과 재진단이 서로 모순되지 않고, 루프 두 번 끝에 재검증이 SLO 충족을 확인하고 종료한다.
3. 각 라운드 값이 4절 범위 안에 있다(2대 1200은 범위의 위쪽, 4대 540은 아래쪽). 5회 중 한쪽으로 좋은 값만 모인 회차가 아니다.

발표에서 함께 말할 점:
- R2 진단 문구의 활성 연결 수 해석은 근거가 약하다(관찰 3). 스케일링 제안의 근거는 문구 끝의 "컨테이너 수 증가로 처리 능력 향상이 기대되어"다.
- 에러율 0.49 → 0.62 → 0.60%는 패널에서 "나빠짐"으로 표시되지만 `/flaky`의 설계된 실패다(3절).
- 대표 사례 하나만 보여주지 않고 4절 범위와 5절 집계(첫 제안 3 / 5, 최종 SLO 충족 2 / 5)를 함께 보여준다.

## 8. 한계

1. **Locust 백분위 근사**: Locust는 응답시간을 반올림해 저장한 뒤 백분위를 구한다(2.46.4 기준 100ms 미만 1ms, 1000ms 미만 10ms, 10000ms 미만 100ms 단위).
   1100·1200·2900~3300은 100ms 단위, 540·550은 10ms 단위 값이다. 그래프 ① 초별 P95는 원시 응답시간으로 계산해 헤드라인과 방식이 다르다.
2. **로컬 단일 PC**: Locust, nginx, target-server replica, Prometheus, 백엔드가 모두 같은 PC(논리 CPU 12개)에서 돈다. 서버를 늘려도 같은 CPU를 나눠 쓴다.
   결과는 이 PC에서의 상대 비교이며, 실제 분산 환경의 확장성을 뜻하지 않는다.
3. **AI 판단 흔들림**: 비슷한 1대 측정값(P95 2900~3300ms)에서 제안 3회, 미제안 2회였다(temperature 0.1). 한 실행 안에서도 재검증과 재진단이 어긋났다(관찰 2).
4. **CPU·메모리 미수집**: Windows Docker Desktop에서 cAdvisor `name` 라벨이 없어 수집하지 못했다. LLM 입력에는 "측정 불가"로 들어가며, 병목 원인을 자원 사용률로 확인하지 못했다.
5. **표본 수**: 50명 5회. 2대는 3라운드, 4대는 2라운드뿐이고, 서버 대수별 라운드 수는 AI 제안에 따라 달라졌다.
6. **저부하 미측정**: 5명 30초 결과 파일이 없어, 이 조건에서 스케일링을 제안하지 않는지 확인하지 못했다(사전 점검 5명 10초 1회는 미제안).
